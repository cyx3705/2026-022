# WBall 验证合同

更新日期：2026-08-01  
适用版本：3.6.0

## 验证原则

- 每项现行需求至少对应一种可重复的验收方式。
- Fast、Full 和 Release Acceptance 分层执行，普通规则修改不得隐式触发长时出片。
- 自动检查不能覆盖的真实窗口标题、AppShell 版本和监听端口必须在发布收口时实跑。
- 未执行、失败和不适用必须明确区分；历史文档中的旧结果不得替代当前运行证据。
- 验证临时目录、`bin/obj` 和出片大文件不提交 Git。

## 环境前提

- Windows 10/11，已安装可构建 .NET 8 目标的 SDK。
- 本机 Roslyn 路径需要时设置 `$env:DOTNET_EnableWriteXorExecute='0'`。
- NuGet 源可读取平级 `2026-023-AppShell` 的正式 AppShell 3.0.3 包。
- 发布包必须自带已登记来源、版本、许可证和 SHA-256 的 Windows x64 FFmpeg 8.0.1；MP4 容器探测是成功条件，PNG 不是降级结果。
- V3.7 权威性能门禁使用当前 i9-13900HX、32 GB 参考机器的本地交互会话；验证器必须记录 Windows、.NET、CPU、活跃显卡与驱动、构建提交、电源状态、远程会话状态和显示分辨率。其它机器的结果只作信息性报告。

## Release Acceptance

V3.6 使用以下收口步骤，不再接受定长 PNG 或 Media Foundation 结果作为证据。

1. 运行 Release 与隔离 Debug 构建，要求 0 警告、0 错误。
2. 运行 Fast、Full、`--render-v36`、`--assist-performance`、`--render-page-smoke`。
3. 用 `--render-v36` 验证 winner-only、四档分辨率、3 秒动画、容器探测、取消与失败事务；长局只验正确性、有界内存和现场隔离，不设生成速度门禁。
4. 运行 `dotnet format .\b-Code-WBall\WBall.sln --verify-no-changes --no-restore` 和 `git diff --check`。
5. 启动 Release `WBall.exe`，确认标题 `WBall v3.6.0`、`AppShell.Shell.dll` 产品版本 3.0.3、WBall 进程 TCP 监听数为 0；只停止本次验证实例。
6. 通过 OHS 执行 `git.rule.scan refresh=true deep=true`，确认本次新增格式受规则管理且无生成物进入提交。

### V3.6 追加验收（已自动化）

1. 静态检查页面与 `render.*` 命令不再公开 `mode`、`seconds`、`maxOutputSeconds`、`mp4`、`keeppng` 或 `render.estimate`；旧参数失败且不创建任务。
2. 以炮台已毁但分别保有经济球、小球库存、炮弹队列和余烬的四类夹具验证阵营仍存活；清除最后价值后只产生一个锁定胜者。
3. 对 720p、1080p、1440p、4K 和合法自定义偶数尺寸生成 MP4，以独立容器探测读取 H.264、宽高、FPS、总帧数和时长；奇数及越界尺寸事务性失败。当前四档与 320x240 自定义均已实测通过。
4. 验证判胜后追加帧数严格为 `3 x FPS`，抽查压暗、高亮、胜者文字和最终定格关键帧；实时与离线使用相同胜者、颜色和动画进度。
5. 分别注入 FFmpeg 缺失、启动失败、管道中断、非零退出、磁盘不足、取消和内部不收敛门限，确认无 `output.mp4`、无 PNG、无残留 partial，manifest 终态和原因准确。
6. 核对发布包内 FFmpeg 的文件版本、SHA-256、来源和许可证登记；运行前后现场哈希一致，BGRA 在途帧与工作集不随总帧数线性增长。

### V3.7 追加验收（已实现，发布时复验）

V3.7 在 V3.6 之后收口。性能门禁与 MP4 出片验收分开运行，出片生成 FPS 和总耗时不属于 V3.7 通过条件。

1. 在改造实时物理前冻结经济区、战斗区和组合舞台三组性能夹具的输入及结果哈希；改造后逐字复验，并继续通过 V3.1、V3.2、V3.5.2 冻结哈希。
2. 使用 Release x64、1920×1080 组合舞台、HUD、四阵营、默认关闭球碰撞、10,000 个经济球和 10,000 个战斗球；预热 30 秒后连续采样 10 分钟。
3. 平均展示帧率必须不低于 30 FPS，P95 帧间隔不超过 50 ms；不得出现超过 200 ms 的 UI 无响应间隔，CommandBus 接收至事务完成的 P95 延迟不超过 100 ms。
4. 2,000 总球数、`1.0x` 时固定步 P95 不超过 16.7 ms；20,000 总球数进入既有 `0.25x` 降速后固定步 P95 不超过 50 ms，模拟步骤和命令队列均无持续积压。
5. 10 分钟峰值工作集不超过 1.5 GiB，预热后增长斜率不超过 5 MiB/分钟，LOH 不持续增长，Gen2 GC 不超过两次；报告须分别记录模拟线程与 UI 线程分配。
6. 以 10,000 总球数、标准密度、开启球碰撞的辅助夹具验证平均 30 FPS和固定步 P95 50 ms，并记录候选配对数，证明没有全量 O(n²) 配对。
7. 跨越 5,000 和 10,000 球阈值验证完整、简化、最小三档及 10% 回升迟滞；所有可见球仍逐球绘制，LOD 前后权威结果哈希一致。
8. 并发发送命令并覆盖开始、暂停、继续、停止、窗口关闭和异常退出，确认 FIFO 固定步提交、事务回显、工作线程、双缓冲和事件订阅均正确释放。
9. 运行 V3.6 出片功能、内存和现场隔离回归，确认出片不启动、不复用或驱动实时模拟协调器；不以出片速度判定 V3.7 失败。

## 开发测试候选

- `Fast` 是默认套件；可组合 `Full`、`RenderSmoke`、`PageSmoke`、`AssistFixes`、`FriendlyAbsorbSmoke`、`GameplayFixes`、`AssistPerformance`、`RuntimePerformance`。`RuntimePerformance` 需要本地可见窗口和 10 分钟采样，不进入普通候选默认套件。
- 测试脚本构建 Debug 并生成单个 `b-Publish/candidate`，不替代 Release Acceptance。
- `development-verification.json` 必须记录 `sourceDirty`；脏工作树允许生成本地候选，但不得进入正式发布流程。
- 新候选先在 `work` 中完整生成和验证，再事务替换；失败时恢复旧候选并保留隔离证据。
- 成功后删除 `work/quarantine`；旧测试候选直接丢弃，`history` 只预留给未来正式包。

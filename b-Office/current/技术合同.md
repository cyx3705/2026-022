# WBall 技术合同

更新日期：2026-08-01  
适用版本：3.6.0

本文件合并当前有效的需求、架构和关键决策。已失效或已被替代的版本方案位于 `../history/`，不得继续作为实现依据。

## 现行需求

### REQ-SIM-001 确定性战斗模拟

- 目的：同一配置、种子和模拟时长必须得到可复核的战斗结果。
- 要求：战斗以固定 60 Hz 时间步推进；输出 FPS 不改变模拟结果；随机序列由显式种子控制。
- 验收：同种子哈希一致，不同种子产生不同结果；冻结回退哈希逐字一致。
- 关联组件：`b-Code-WBall/App/Battle/`、`b-Code-WBall/Core/Recording/TimelineClock.cs`
- 关联验证：`VERIFY-FULL`

### REQ-BAL-001 可配置战斗平衡与隔离试跑

- 目的：玩法参数可调整且不会因试跑污染当前战局或用户配置。
- 要求：规模与平衡分别由 `arena_layout.json` 和 `battle_balance.json` 表达；`balance.*` 命令与设置 UI 等价；`balance.sim` 使用隔离实例并支持多种子、超时、取消和 CSV/表格结果。
- 验收：合法输入完整生效，非法输入失败且不产生部分写入；隔离试跑前后现场状态与配置不变。
- 关联组件：`b-Code-WBall/Core/Battle/`、`b-Code-WBall/App/Commands/BalanceCommands.cs`
- 关联验证：`VERIFY-FULL`

### REQ-RENDER-001 结果导向离线出片（已由 REQ-RENDER-002 替代输出语义）

- 目的：录制不依赖实时抓屏，球数较多时仍能稳定生成完整结果。
- 保留要求：冻结输入后在独立双世界中计算不可变画面帧，经有界队列交给专用 STA 消费者组合；不得重置现场，也不得把整片 BGRA 常驻内存。
- 替代说明：定长、PNG 和 Media Foundation 输出已在 V3.6 退役，现行输出与验收以 `REQ-RENDER-002` 为准。
- 关联组件：`b-Code-WBall/App/Recording/`、`b-Code-WBall/Core/Recording/`
- 关联验证：`VERIFY-RENDER`、`VERIFY-ACCEPT`

### REQ-RENDER-002 V3.6 MP4 胜者出片（已实现）

- 目的：将出片收敛为从冻结场景计算到唯一胜者、追加胜利动画并直接交付 MP4 的单一流程。
- 要求：删除模式、用户时长、最长输出、时长估算和 PNG/MP4 选择；分辨率支持预设及 `320x240..7680x4320` 范围内的偶数自定义尺寸；阵营只有在炮台死亡且经济球、库存、队列、在场弹体及待吸收价值全部归零后才淘汰；判胜后冻结战局并追加固定 3 秒动画；BGRA 帧通过随应用发布的固定 FFmpeg 流式写入 H.264 MP4，不生成 PNG 中间产物或失败降级。
- 失败语义：编码失败、取消或内部 24 小时视频时间仍未收敛时不得生成成功 MP4 或伪胜者；无效 partial 删除，错误 manifest 保留。旧配置字段只忽略并在后续保存时移除，不删除用户历史结果。
- 验收：`--render-v36` 已覆盖 winner-only 接口、完整可战价值、胜者锁定、`3 x FPS` 动画、720p/1080p/1440p/4K 与自定义分辨率、H.264 容器、取消/缺失编码器事务、现场隔离和冻结哈希；旧 PNG/Media Foundation 输出语义已被替代。
- 关联规格：`../history/WBall_v3.6_MP4胜者出片与胜利动画需求.md`
- 关联验证：`VERIFY-RENDER-V36`、`VERIFY-ACCEPT`

### REQ-PERF-001 V3.7 高容量实时性能（已实现，待顺序发布）

- 目的：在不减少模拟实体或改变比赛结果的前提下，使高球数实时舞台保持稳定展示和可响应交互。
- 要求：实时模拟由单一工作线程独占可变世界，CommandBus 写操作按 FIFO 在固定步边界提交；WPF 只消费不高于 30 Hz 发布的双缓冲只读帧快照，允许丢弃过期展示快照但不得丢模拟步骤。经济区静态对象和两类球交互使用随场景版本更新的索引及可复用空间哈希；固定步热路径不得持续创建临时分组、排序和全球扫描集合。绘制缓存静态层并合并 Dispatcher 失效；5,000 与 10,000 球形成三档自动视觉 LOD，回升阈值使用 10% 迟滞。
- 不变量：LOD 只降低轨迹、文字、光晕和粒子等展示细节；每颗可见球仍显示位置、颜色和半径。不得合并、删除或抽样模拟实体，不得改变固定步、随机顺序、碰撞、吸收、积分守恒、场景格式或冻结哈希。
- 验收：参考机器以 Release x64、1080p 组合舞台、四阵营、10,000 个经济球与 10,000 个战斗球运行，预热 30 秒后持续 10 分钟，平均展示不低于 30 FPS、P95 帧间隔不超过 50 ms、CommandBus P95 延迟不超过 100 ms、无超过 200 ms 的 UI 停顿；2,000 球全速固定步 P95 不超过 16.7 ms，20,000 球在既有 `0.25x` 降速下固定步 P95 不超过 50 ms且无持续积压；峰值工作集不超过 1.5 GiB，预热后增长不超过 5 MiB/分钟，LOH 不持续增长，Gen2 GC 不超过两次。
- 出片边界：V3.6 MP4 出片继续冻结输入并使用独立世界逐帧计算，不消费实时工作线程或帧快照，不追赶墙钟；V3.7 不设置出片吞吐或总耗时门限，但不放宽有界内存、正确性和现场隔离合同。
- 关联规格：`../history/WBall_v3.7_高容量实时性能与线程隔离需求.md`
- 关联验证：`VERIFY-PERF-V37`、`VERIFY-FULL`、`VERIFY-ACCEPT`

### REQ-ASSIST-001 友军积分传递与小球吸收

- 目的：大球完整回收同阵营小球并接收较小大球积分，同时抑制小球无限积累。
- 要求：球碰撞与友军吸收是互斥模式。默认关闭球碰撞并启用吸收；缺少 `ballInteractionRulesVersion` 的旧 arena 配置必须一次性迁移到该默认值，迁移后用户主动开启碰撞的选择必须继续持久化。手动开启球碰撞后，大小球吸收和大球互吸全部停止。同阵营大球的光环与小球重叠时，小球实体必须当帧回收，其全部积分必须在同一帧等量增加到接收大球，不得进入延迟池或受旧 `FriendlyAbsorbSmallRate` 限速；小球之间永不吸收。较大大球吸收较小大球积分，相同值时按确定性随机规则选择一方，大球路径仍受 `FriendlyShellTransferRate` 低速预算限制。接触判断必须覆盖普通接触和单帧高速穿越。
- 验收：持续 120 帧注入 960 点小球后，大球从 100 精确增至 1060，小球存活峰值和待吸收值均为 0；小球与小球重叠后数值和实体不变；开启球碰撞后大小球及大球互吸均不发生；大球路径的清空、同值选择、守恒和预算上限通过；1 万球性能门禁通过。
- 关联组件：`b-Code-WBall/App/Battle/BattleRuntime.cs`
- 关联验证：`VERIFY-FULL`、`VERIFY-PERF`

### REQ-SHIELD-001 大球破盾后反弹

- 目的：避免单发大球连续破盾并直接触杀炮台导致对局过快结束。
- 要求：护盾中央显示 `Shield / ShieldCostPerValue` 向下取整后的可抵消积分；护盾增长不受旧 `MaxShield` 字段封顶，设置窗不再提供护盾上限，旧字段只保留文件兼容。初始护盾、护盾槽、自家小球返还和自然恢复均可持续增长到 `double` 的可表示范围。炮台护盾外圈的进度为 `本方当前护盾 / 四方当前护盾总值`，四方总值为 0 时显示 0%；实时舞台与离线出片必须共用该公式。大球和升格小球均与护盾逐点等量抵消，护盾不足时保留弹体剩余积分；落球区小球进入“护盾”槽时，1 点小球积分按 `ShieldSlotGainPerValue` 转换为对应数量的可抵消护盾点，再乘 `ShieldCostPerValue` 写入底层护盾值。`slotGain` 的 0~100 按可抵消点倍率解释，历史较大值继续按原始护盾单位解释；大球破盾后必须反弹；`breakthrough` 不得由命令、UI 或持久化 JSON 重新开启。
- 验收：旧上限 1000000 的炮台经护盾槽加盾后可增长至 1150000，初始护盾和自然恢复均可超过旧上限；四方护盾 100/400 时外圈为 25%；护盾 5 点遇到小球 1 点后显示 4；护盾 3 点遇到升格小球 5 点后护盾归零且小球剩 2；满盾被大球打破后炮台存活、大球反向且剩余积分正确；非法 `breakthrough` 参数明确失败。
- 关联组件：`b-Code-WBall/App/Battle/BattleRuntime.cs`、`b-Code-WBall/Core/Battle/BalanceConfig.cs`
- 关联验证：`VERIFY-FULL`

## 系统架构

### 系统边界

WBall 拥有落球与战斗模型、业务用例、命令、WPF 视图和离线出片适配。AppShell 提供桌面外壳、停靠与公共命令契约；Windows 提供 WPF。V3.6 随应用发布固定 FFmpeg 8.0.1，通过独立进程标准输入编码 H.264 MP4。WBall 不拥有 AppShell 源码、网络服务或 OHS 项目管理能力。

### 组成

| 组件 | 路径 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| Core | `b-Code-WBall/Core/` | 模型、平衡配置、公式、时间轴与纯逻辑 | 配置、种子、时间步 | 可序列化状态与纯计算结果 |
| Application | `b-Code-WBall/Application/` | 编辑用例、校验和事务提交 | 编辑请求、存储抽象 | `EditResult` 与更新后的权威状态 |
| Battle | `b-Code-WBall/App/Battle/` | 对局编排、经济桥和战斗运行时 | Core 状态、命令与时间步 | 战斗世界、比分与帧投影 |
| Commands | `b-Code-WBall/App/Commands/` | 将控制台和 UI 参数适配到用例/运行时 | 命令文本 | `CommandResult` |
| Presentation | `b-Code-WBall/App/Presentation/`、`b-Code-WBall/App/Stage/` | AppShell 窗口、场景调试、舞台和 HUD | 权威世界状态 | WPF 交互与画面 |
| Recording | `b-Code-WBall/App/Recording/` | 独立世界计算、胜利帧组合和 FFmpeg 流式编码 | 冻结任务快照 | MP4 与 manifest |
| Verification | `b-Code-Verify/` | 快速规则验证、完整回归和发布验收 | 代码与冻结基线 | PASS/FAIL 摘要和临时证据 |
| Test Candidate | `b-Code-WBall/eng/`、`b-Publish/` | 构建并事务替换单个本地 Debug 测试候选 | 源码与指定验证套件 | 可运行应用与开发验证报告 |

### 关键流程

1. 实时对局：由单一实时工作线程按固定步结算经济、弹药、护盾、火力和战斗；CommandBus 在固定步边界串行提交，舞台消费有界双缓冲只读帧快照，WPF 不再推进实时模拟。
2. 编辑：View 组装命令，CommandBus 调用领域命令，Application 用例完成解析、校验和一次性提交，`SceneWorld.Changed` 驱动刷新。
3. 离线出片：冻结现场输入，在独立世界计算帧投影，经有界生产者/消费者队列交给 STA 组合与流式编码。
4. 版本验证：Fast 先验证纯规则，Full 再验证确定性和桌面组合，发布收口才执行长时出片与真实启动。

### 不变量与生成物边界

- Core/Application 不得反向引用 Desktop、WPF、AppShell 或 Media Foundation。
- 用户权威数据位于 `%AppData%/WBall/`，仓库内 `bin/`、`obj/`、`artifacts/` 和验证临时目录均可重建且不入库。
- 场景、布局、预设和录制任务不得因版本补丁被静默删除或整体重置。
- `ShieldBreakthrough` 只允许作为 `[JsonIgnore]` 的旧哈希内存兼容字段存在。
- v3.1 回退配置哈希：`7231013A2B055BF00CA51012343A071055178F697C947792A1A7BFA96254DD65`。
- v3.2 回退配置哈希：`AAD5428D2F251BE5F31451B4B94971D2ADBBC8B1F6979340CCA2D2CB058C1D74`。

## 有效决策

### DEC-001 固定消费 AppShell 3.0.3

- 状态：已接受
- 日期：2026-07-29
- 决策：只通过固定版本 NuGet 包消费 AppShell，不复制或修改框架源码。
- 原因：框架边界稳定，WBall 只维护业务差异。
- 后果：框架需求必须进入 `2026-023-AppShell`，WBall 不得本地打补丁。

### DEC-002 编辑写入统一经过 CommandBus

- 状态：已接受
- 日期：2026-07-29
- 决策：UI 只适配参数，业务校验和事务提交位于 Application 用例。
- 原因：避免 UI、控制台和测试形成三套规则。
- 后果：新增编辑功能必须先定义用例与命令等价入口。

### DEC-003 录制采用离线帧组合

- 状态：已接受
- 日期：2026-07-28
- 决策：录制是组合计算好的画面帧，不抓取实时视频；球数过多时按确定性曲线降低模拟速度。
- 原因：把结果完整性从现场帧率和 UI 卡顿中解耦。
- 后果：出片必须使用独立世界和有界队列，不能复用或重置现场世界。

### DEC-004 友军吸收互斥且破盾必反弹

- 状态：已接受
- 日期：2026-07-30
- 决策：小球由大球即时等值吸收，大球互吸仍按时间预算；球碰撞与友军吸收互斥且默认关闭碰撞；破盾大球不再直入炮台。
- 原因：延迟池让画面数值看起来没有真正增长，物理碰撞会与吸收接触互相干扰，破盾直入则导致对局过早结束。
- 后果：当前默认哈希及 v3.1/v3.2 回退配置哈希升级为新的 v3.5.2 基线；专项门禁必须同时验证吸收模式和碰撞模式。

### DEC-005 现行合同与历史版本分离

- 状态：已接受
- 日期：2026-07-30
- 决策：`current/` 只维护三份现行合同，版本需求和阶段记录归档到 `history/`。
- 原因：降低上下文成本，避免过期需求覆盖当前实现。
- 后果：后续需求更新本合同，不再默认新增 `WBall_vX.Y_*.md` 活动文件。

### DEC-006 本地测试候选采用单槽事务

- 状态：已接受
- 日期：2026-07-30
- 决策：`b-Publish/candidate` 只保留最近一次通过指定套件的 Debug 候选；`work/quarantine` 仅服务当前事务；普通测试候选不写入 `history`。

### DEC-007 V3.6 出片采用 MP4-only 胜者流水线

### DEC-008 V3.7 实时模拟线程隔离与视觉降级

- 状态：已规划，待实现验证
- 日期：2026-08-01
- 决策：实时可变世界只由单一模拟工作线程持有，WPF 通过双缓冲只读帧快照以 30 Hz 展示；高球数只降低视觉细节，不减少、聚合或抽样权威模拟实体。MP4 出片保留独立世界和独立生命周期，不复用实时模拟协调器，也不设置生成速度门限。
- 原因：当前 UI 定时器同时承担固定步模拟和全量 WPF 绘制，多源失效、重复扫描和当帧分配会在球数增长时共同阻塞 Dispatcher；仅优化单个友军助力微基准无法证明现场流畅。
- 后果：所有运行时写操作必须经 CommandBus 排队到固定步边界，视图不得直接读取可变球集合；`VERIFY-PERF-V37` 已覆盖 2 万球、30 FPS、交互、GC、内存、哈希和生命周期门禁。V3.7 实现虽已通过，仍须等待 V3.6 后按顺序发布。

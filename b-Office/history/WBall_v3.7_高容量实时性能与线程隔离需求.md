# WBall V3.7 高容量实时性能与线程隔离需求

> 文档性质：V3.7 版本需求规格  
> 目标版本：**3.7.0**  
> 文档日期：2026-08-01  
> 前置版本：V3.6 MP4 胜者出片  
> 当前稳定基线：V3.5.2  
> 当前状态：**实现与性能门禁完成，待 V3.6 顺序集成及版本发布**

---

## 1. 版本目标

V3.7 对实时舞台进行一次以结果为准的性能升级：在当前参考机器上，以 Release x64、1920×1080 组合舞台、四阵营、10,000 个经济球和 10,000 个战斗球为标准场景，稳定展示不低于 30 FPS，并使窗口、命令和暂停操作保持可响应。

性能升级不得通过删除、合并或跳过模拟实体换取帧率。球数过高时只允许降低轨迹、文字、光晕和粒子等视觉细节；每颗在场球仍按既有固定步、随机顺序、碰撞、吸收、护盾与积分规则参与计算。

V3.7 不改变 V3.6 出片语义。MP4 出片继续冻结输入并使用自己的独立世界逐帧计算，不消费实时舞台的工作线程或帧快照，也不以墙钟时间追赶现场模拟；本版本不为出片总耗时或生成 FPS 设置性能门限。

## 2. 当前基线与问题

### 2.1 参考环境

权威性能门禁以当前参考机器为准：Intel Core i9-13900HX、32 GB 内存、Windows 10/11。显卡、驱动、Windows 构建、.NET 运行时、应用提交、构建配置、电源状态和显示分辨率必须由验证器在每份报告中重新记录，不依赖文档中的静态机器描述。

### 2.2 已确认热点

- `BattleRuntime.cs` 约 1,732 行，固定步内存在空间桶、分组、排序、阵营配对和全量计数的重复分配与扫描。
- `DropZoneView.cs` 约 1,100 行，按约 16 ms 定时器全量绘制经济对象、轨迹和球，部分几何及画刷仍在当帧创建。
- `RenderJobService.cs` 约 811 行；`StageFrameRenderer.cs` 每帧创建完整 WPF 离屏对象和 BGRA 数组。该路径属于独立出片，不纳入 V3.7 实时吞吐门禁。
- 经济区 `PhysicsEngine.Step` 对每颗球重复枚举静态方块、异形、重力箭头和销毁器；传送等路径仍创建临时列表，开启球碰撞时配对成本可退化为 O(n²)。
- `StageView`、`DropZoneView` 使用独立 16 ms `DispatcherTimer`，世界、战斗与导演事件又分别排队 `InvalidateVisual`，同一帧可能出现重复失效。
- 当前 `VERIFY-PERF` 只测量 10,000 个战斗球、3 个固定步下友军助力的相对开销。最近结果约为关闭 14.769 ms、开启 14.766 ms、1.0x；该数字不代表真实经济物理、WPF FPS、GC、持续内存或交互响应。

V3.7 实施前必须先用新夹具保存改造前的 CPU、UI、GC、内存和哈希基线，不得用上述微基准代替完整门禁。

## 3. 实时线程与状态所有权

### 3.1 单一模拟工作线程

- 新增实时模拟协调器，由一个专用工作线程独占经济世界、战斗世界、导演和运行时计数器的可变状态。
- 固定步仍为 60 Hz，`TimelineClock` 的确定性球数降速公式保持不变；不得根据墙钟抖动、渲染速度或机器负载跳过固定步。
- CommandBus 是唯一写入入口。运行中的写命令进入 FIFO 队列，在下一个固定步边界按接收顺序完整应用；暂停或编辑态命令由协调器立即串行应用。
- 命令只有在变更已成功提交或事务性失败后才返回结果。非法输入、取消和线程关闭不得产生部分写入。
- 启动、暂停、继续、停止、窗口关闭和异常退出必须有明确状态机；工作线程、等待中的命令和事件订阅均能终止，不留下后台线程或悬挂等待。

### 3.2 双缓冲只读帧快照

- WPF 视图不得遍历工作线程正在修改的 `SceneWorld.Balls` 或其它可变集合。
- 协调器以不高于 30 Hz 的展示频率发布完整只读帧快照，至少覆盖两个世界的尺寸、球投影、场景对象、炮台、阵营统计、HUD 数据和必要效果状态。
- 快照使用可复用双缓冲或等价有界缓冲；发布后内容不可修改，UI 释放后才能重新写入该槽。
- UI 永远消费最新完整快照。旧展示快照允许丢弃，但模拟步骤、命令、伤害、吸收和积分结算绝不允许丢弃。
- 经济世界、战斗世界、导演和 HUD 的变化合并为一次发布信号；Dispatcher 同一时刻最多存在一个待处理刷新任务。

## 4. 物理、索引与分配治理

### 4.1 经济区

- 方块、异形、重力箭头、槽位、生成器、销毁器及传送目标按场景版本建立类型索引和空间索引；只有场景成功提交后才重建。
- 球与静态对象查询只访问相交或邻近单元，不得为每颗球重新枚举全部场景对象。
- 球碰撞使用可复用均匀网格或等价空间哈希，配对顺序必须稳定，同一对球每步最多处理一次。
- 传送目标、销毁器和公式查找不得在固定步创建临时 `List`、LINQ 枚举器或字符串键集合。

### 4.2 战斗区

- 弹体碰撞、友军吸收、光环接触和阵营交互共用可清空复用的空间桶及候选缓冲，不得每步重建字典、列表、`HashSet` 或排序结果。
- 用稳定 ID、稳定插入顺序和显式比较器保持现有确定性；性能改造不得通过无序并行计算改变同帧结算顺序。
- 阵营球数、各角色弹体数、弹药和可战价值维护增量计数；每个确定间隔执行全量审计，发现漂移时验证门禁失败，不得静默修正后继续。
- 只在本次性能路径涉及处拆分 `BattleRuntime`，不借机重写玩法或更改公开配置结构。

### 4.3 分配约束

- 固定步热路径使用预分配、容量复用或受控池化缓冲；不得把池化对象暴露给用户数据或跨任务共享可变状态。
- 集合容量可按历史峰值增长，但不得按帧缩容；场景重置、停止和窗口关闭后必须释放超大缓冲引用。
- 性能报告必须分别记录模拟线程与 UI 线程的分配、Gen0/1/2 GC、LOH 大小、私有字节和工作集。

## 5. 实时绘制与自动视觉 LOD

### 5.1 绘制缓存

- 背景、槽位、边界、炮台静态层、冻结画刷、画笔和不变几何按场景版本缓存；仅在尺寸、颜色、场景或主题实际变化时失效。
- 视口外对象不进入当帧绘制命令，但仍完整参与物理和积分计算。
- 动态球使用低分配批量绘制路径；不允许为每颗球每帧创建新的画刷、画笔、文本布局或独立 WPF 控件。
- DropZone、Arena 和 HUD 必须从同一帧快照绘制，禁止一个展示帧混用不同模拟时刻的数据。

### 5.2 LOD 档位

| 档位 | 进入球数 | 展示要求 |
| --- | ---: | --- |
| 完整 | `< 5,000` | 保留当前轨迹、逐球文字、光晕和完整效果 |
| 简化 | `5,000..9,999` | 缩短轨迹，降低逐球文字和粒子刷新频率，复用效果几何 |
| 最小 | `>= 10,000` | 每颗可见球仍显示位置、颜色和半径；关闭逐球文字、高成本光晕及非必要粒子 |

- 从高档回升到低档时，球数必须低于对应进入阈值的 90%，形成 10% 迟滞。
- LOD 只由当前总存活球数决定，不增加用户可调性能参数；当前档位可写入诊断日志和验证报告，但不新增日常设置入口。
- 超过 20,000 球继续使用最小档和既有确定性模拟降速，不承诺更高球数仍达到 30 FPS，也不得引入额外模拟降级。
- 离线 MP4 不使用实时 LOD；出片画质和时间轴继续由 V3.6 合同定义。

## 6. 性能门限

### 6.1 标准场景

使用 Release x64、1920×1080、组合舞台与 HUD、四阵营、默认关闭球碰撞、10,000 个经济球加 10,000 个战斗球。场景、种子、初始位置和运行脚本固定入验证器；预热 30 秒后连续采样 10 分钟。

标准场景必须同时满足：

- 平均展示帧率不低于 30 FPS，P95 帧间隔不超过 50 ms。
- UI 不出现超过 200 ms 的无响应间隔；CommandBus 操作从接收到提交完成的 P95 延迟不超过 100 ms。
- 2,000 总球数、`1.0x` 全速时固定步 P95 不超过 16.7 ms。
- 20,000 总球数进入既有 `0.25x` 降速后，固定步 P95 不超过 50 ms且没有未消费固定步持续积压。
- 10 分钟峰值工作集不超过 1.5 GiB；预热后线性增长斜率不超过 5 MiB/分钟；LOH 不得持续增长，Gen2 GC 不超过两次。

另设 10,000 总球数、标准密度、开启球碰撞的辅助门禁，要求平均展示帧率不低于 30 FPS、固定步 P95 不超过 50 ms，并以候选对数量证明已退出全量 O(n²) 配对。所有球重叠等病理输入只要求可诊断和可取消，不得通过跳过合法碰撞伪造性能通过。

### 6.2 测量规则

- 报告同时输出平均值、P50、P95、P99、最大值和样本数，不得只报告最好结果。
- 硬门限仅在参考机器的本地交互会话中判定；其它机器仍生成完整报告，但标记为信息性结果。
- 验证器必须记录活跃显示适配器、远程会话状态和电源状态；远程桌面、节能模式或调试器附加时不得把失败写成正式性能结论。
- 首次 JIT、场景加载和 30 秒预热不计入稳态指标，但启动峰值仍记录在报告中。

## 7. 验证接口与证据

新增 `VERIFY-PERF-V37`，入口固定为：

```text
dotnet run --project .\b-Code-Verify\WBallVerify\WBallVerify.csproj \
  -c Release -- --runtime-performance
```

该套件与 `--assist-performance` 分离，并生成 JSON 报告。报告至少包含环境、输入场景哈希、固定步耗时、展示帧间隔、命令延迟、快照发布/丢弃数、候选配对数、分配、GC、LOH、私有字节、工作集、LOD 档位停留时间和最终状态哈希。

实施前冻结三组性能夹具的权威输入与结果哈希：经济区、战斗区、组合舞台。实现后相同输入必须逐字一致，并继续通过 V3.1、V3.2、V3.5.2 冻结哈希。若仅展示快照或 LOD 改变，不得升级玩法哈希。

## 8. 出片隔离边界

- 出片任务不启动、不复用也不驱动实时模拟协调器；实时舞台是否处于编辑、暂停或播放状态不能改变出片结果。
- 出片使用冻结配置创建自己的经济世界、战斗世界、导演、时间轴、帧队列和编码器生命周期。
- 出片只按视频帧时间推进独立计算，不追赶墙钟；机器快慢只影响等待时间。
- V3.7 不规定 720p、1080p或 4K 的生成 FPS、实时倍数或完成时长，不得为了提高出片吞吐降低画质、丢帧或修改模拟倍率。
- V3.6 已定义的有界内存、取消、MP4 完整性、现场隔离和确定性要求继续有效。

## 9. 版本边界与完成定义

- 不修改 AppShell 3.0.3 源码，不新增默认网络监听，不开启 WBall MCP。
- 不迁移用户场景、布局、配置、预设和已有录制目录。
- 不新增用户可调线程数、空间桶尺寸、帧率或 LOD 阈值。
- 不把并行物理、实体聚合、抽样模拟或近似积分引入权威结果。
- V3.7 实施前不得把程序集、窗口标题、项目概览或验证摘要标记为 3.7.0 已完成。

只有线程所有权、只读快照、空间索引、低分配绘制、自动 LOD、标准性能门限、命令响应、内存红线、冻结哈希和生命周期门禁全部通过，才能将 V3.7 状态改为“已完成”。

## 10. 2026-08-01 实施结果

V3.7 性能实现与独立门禁已经完成，但当前稳定产品版本仍为 V3.5.2，V3.6 仍待实施。V3.7 不越过 V3.6 提前修改程序集版本、窗口标题或发布包版本；后续应在 V3.6 完成后按版本顺序集成发布。

已交付的实现包括：单一实时模拟工作线程、固定步边界命令串行化、双缓冲只读帧快照、30Hz 绝对节拍且至多一个 Dispatcher 请求、经济区静态空间索引、可复用球碰撞与战斗空间桶、增量/低分配热路径、三档自动 LOD、逐球位图层、静态绘制与 HUD/炮台缓存，以及独立于实时协调器的出片回归。

权威 `VERIFY-PERF-V37` 使用 Release x64、1920×1080、四阵营、10,000 个经济球加 10,000 个战斗球，预热 30 秒后持续采样 10 分钟，结果如下：

- 平均展示 29.997 FPS（按 30 FPS 目标的计时容差通过），P95 帧间隔 47.298 ms，最大间隔 90.913 ms，无超过 200 ms 的 UI 卡死。
- CommandBus P95 完成延迟 5.627 ms；2,000 球固定步 P95 3.596 ms；20,000 球固定步 P95 8.223 ms。
- 20,000 球双缓冲快照 P95 0.373 ms；辅助离屏 WPF P95 38.704 ms。
- 峰值工作集 283.574 MiB，预热后斜率 0.074 MiB/分钟，Gen2 GC 0 次，LOH 增长 0 MiB。
- Release 构建 0 警告、0 错误；Fast 14/14、Full 100/100、页面 smoke 与出片现场隔离 smoke 全部通过。
- V3.1、V3.2、V3.5.2 seed 42/43 的冻结哈希保持不变。

详细逐样本数据由验证器 JSON artifact 保存，本需求文档只维护结论，不复制完整日志。
